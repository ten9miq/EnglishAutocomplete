# 実アプリ・IME・共存の手動試験

下表には実アプリでの未検証項目を含む。別プロセスの専用Win32 Edit fixtureによる自動試験と区別する。個人文書ではなく新しい空の試験用文書を使い、最初はLearning=0で確認する。

## 対応入力欄での手順

1. 新規の試験用文書、ENG、Learning=0で開始。既定のMinLength=2で`c`では候補なし、`co`まで入力すると初期5候補が表示されること。続けて`confi`にし、候補が更新されてフォーカスが入力欄に残ることを確認。
2. Ctrl+Alt+Down/Upで選択表示が変わること。Ctrl+Alt+Spaceで既存`confi`を残した語尾だけが入ること。改行・Tab・空白の自動挿入がないこと。
3. Tabで選択開始後、数字2（通常列とテンキー両方）で2番の候補を確定。選択前の数字は文字として入ること。表示件数より大きい番号キーは元のアプリへ渡ること。Escで非表示、既存文字は残ること。
4. BSで入力文字と候補が短くなること。通常のDelete、左右/Home/End/PageUp/PageDown、選択操作、削除用×以外のクリック、ホイールでは候補を閉じること。
5. コピー、貼り付け、切り取り、Undo/Redo、アプリ側の自動補正で古い候補を確定できないこと。入力済み単語の中間位置では補完しないこと。
6. 入力中に同じ窓の別欄/別アプリへ切り替え、確定キーを押しても前の欄へ文字を送らないこと。
7. Tab/Enterを無効のまま通常操作を確認。その後試験アプリだけで明示有効にし、候補がない時は通常操作、候補がある時は補完だけになることを確認。
8. `COM`/`Com`/CamelCaseを入力し、入力済み表記を削除せず適切な語尾だけが追加されること。
9. 日本語IMEへ切り替えて未確定入力を作り、英文候補も学習も生じないこと。ENGへ戻して新しい単語から再開すること。
10. MS-IMEをONの半角英数にして、TextEditPattern対応のRichEdit等で`confi`を入力。候補表示と語尾追加を確認する。IME OFFとして照会される「A」はONの半角英数試験に含めない。標準Editなど照会できない欄では候補が出ないこと。
11. 候補表示中にマウスでひらがな・全角英数へ変更し、確定キー・Tab/Enter/Escが元のアプリ/IMEへ渡ること。半角英数のまま未確定入力/再変換を作れる場合も、候補確定・学習が止まること。取消後は新しい単語から再開すること。
12. 候補表示中にIME OFF→ON、mode 0→16等の許可状態間の変更を行い、変更前の候補を確定できないこと。照会エラー/応答遅延/フォーカス喪失時も補完せず、本文・クリップボードを変更しないこと。

### 初期5→9候補・IME風キー操作（2026-11-09変更）

- IME OFFで`confi`を入力し、初期5件が未選択（背景ハイライトなし）であること。最初のTab/↓で1件目、その後は次候補へ進むこと。5番目を選んだその表示から9件へ展開すること。4番へ戻っても9件を維持し、通常文字・取消・次の語で初期5件へ戻ること。未選択のShift+Tab/↑は9件目へ移り同時に展開し、その後は前候補へ進むこと。
- 候補表示中・選択モード中でもSpaceとShift+Spaceで普通の空白が入力され、候補を選んだり確定したりしないこと。空白入力で候補と選択モードが終了すること。Ctrl+Alt+Spaceの明示確定は維持する。
- 選択開始前の数字は文字入力。Tab後の数字1～5・テンキー1～5で対応候補の語尾だけが入ること。展開前の6～9は文字入力、展開後は候補確定になること。IME ON・ImeStyle=0・対象外欄では数字を横取りしないこと。
- 選択開始前のEnterは入力先へ渡り、選択モード中だけ候補の語尾を追加すること。確定後は選択モードを終了し、改行/送信を重ねて実行しないこと。
- 確定Enterを長押し/リピートしても確定は1回・改行0回になること。キーを離してから別にEnterを押すと通常の改行/送信だけになること。短い押下でkeyupが先に処理されてもEnterが効かなくなる状態を残さないこと。
- Esc・空白・通常文字・左右移動・クリックで選択を終了すること。候補なし・対象外・キー無効アプリではTab/矢印/Enterを横取りしないこと。Space/Shift+Spaceは状態に関係なく候補操作へ割り当てないこと。Ctrl+Alt+Tabを登録しないこと。
- IME ONでは半角英数を含めスクリプトの候補と選択を停止し、MS IME等のSpace/Tab/矢印/Enterが働くこと。IME ONへ切り替える前の候補を確定できないこと。
- `ImeStyle=0`のアプリではIME風キーを使わず、既存の明示ショートカットだけになること。

状態遷移92項目、専用Win32 Editで実OnChar/実ホットキー28項目（初期5件・5番で9件・Tab→数字3/9・Enterリピート抑制）を自動確認。後続のChrome専用localhostフォームの手入力試験では、候補表示・Tab→3・Tab→Enter・未選択Enterを確認した（docs/VALIDATION.md参照）。初期5→9行の実表示、任意のWebアプリ、合成OSキー自動試験、Codexでの新UI・新キーは未確認。

## 学習と安全

### 選択した学習候補の削除

- 試験用の未知語を2回学習し、接頭辞からTab/矢印で選択する。その行だけ右端に「×」が現れること。Ctrl+Deleteで履歴を消すと未知語が候補から消え、入力済み文字を消さず、選択モードも終了すること。長押しでも他の候補や入力文字を続けて削除しないこと。
- 別の学習済み未知語で「×」をクリックし、元の入力欄にフォーカスとキャレットが残り、単語確定・改行・送信が起きないこと。候補更新直前の古い行やフォーカス移動後の操作で別の語を消さないこと。
- 配布辞書にもある学習語は履歴だけ消え、通常候補には残って「×」が消えること。手動登録語・未学習語には「×」がなく、この操作で削除しないこと。禁止状態も保持すること。
- 未選択・未学習語選択・候補なし・IME ON・対象外欄では新しいCtrl+Deleteを入力先へ渡すこと。`Keys=0`では両方の削除を無効にすること。DBロック時に表示上だけ削除しないこと。未知語は後で意図して2回入力すれば再学習できること。
- 100～300%のDPIと5→9件展開で×が選択行の右端に収まり、候補文字・訳を覆わず、文字開始位置のキャレットX合わせを維持すること。

- 試験用にLearning=1へ変更し再読込。未知語`MyInternalTool`を空白区切りで2回手入力し、1回では個人候補にならず、2回後に候補になること。既存DBの2回履歴も再読込後に候補になること。
- 手動登録した`config.toml`/`php-fpm`/`Tool2`は即候補になること。自動学習ではこれらを登録しないこと。
- 学習ONの安全な試験欄で、候補選択を繰り返すと使用回数と最終使用日時が増え、優先度に反映されること。Chrome/Codexも既定Learning=1で同様に学習すること。明示的にLearning=0へ設定したアプリでは回数が追加されないこと。
- 再起動後も表記・回数が残ること。禁止語は標準辞書候補からも消え、delete後は再登録可能であること。
- 未登録アプリやEnabled=0でもLearning=1なら安全な対応欄で学習し、候補表示・キー横取りはしないこと。Tabがフォーカスを移した場合、その語は学習しないこと。パスワード欄、readonly、除外アプリ、未対応欄、Learning=0ではDBに単語が増えないこと。メール・URL・テスト用の認証文字列が入らないこと。本物のパスワードやトークンでは試さない。
- 入力欄判定が不明な時に機能が止まること。文書の全文やキー履歴がstatus.log等へ残らないこと。
- DBの書込不可/ロック/破損では学習が止まり本体がクラッシュしないこと。実データではなくバックアップした試験DBで行う。

## 辞書の所有格候補

- `teacher`/`computer`では訳のない`teacher's`/`computer's`が通常候補に混ざらないこと。`teacher'`/`computer'`まで入力すれば所有格を補完できること。
- `it'`では`it's`、`let'`では`let's`など短縮形が残ること。訳のある見出しと手動登録した所有格は利用できること。辞書生成・AHK検索の回帰試験あり。

## 共存・DPI・長時間試験

- 既存IME表示だけの負荷を採取した後、補完を追加して同じ条件で採取する。既存スクリプトを勝手に終了・再起動しない。補完だけの比較は既存表示を終了してよいと利用者が明示した環境で別途行う。
- 補完GUIは既定で候補文字の開始位置をキャレットXへ合わせる（OffsetX=0）。番号欄・左余白は左側へ出し、画面端では枠全体を画面内へ収める。5→9行へ展開しても文字の横位置がずれないこと。横位置修正後、利用者から「おおむねちょうどよい」と回答あり。アプリ別の厳密な座標比較は未実施。
- 縦余白は24px(96DPI基準、150%では36物理px)。Chrome・サクラの下置きはキャレット下端→候補上端、Codex等の上置きはキャレット上端→候補下端に同じ余白を取り、入力行へ重ならないこと。5→9行の展開後も上置きの候補下端との余白を維持すること。IME表示・変換候補・アプリの補完との実際の距離は別途目視し、必要ならOffsetYを調整する。利用者から縦位置は「おおむねちょうどいい」と回答あり。アプリ別の詳細な目視計測は未実施。
- 100/125/150/175/200/225/250/300%で、11ptが二重拡大されず、日本語と番号列の上下が欠けず、白地・細い枠・番号列・淡い青の選択背景が読めること。長い訳文、`&`、改行を含む訳文でも1行に収まり、長い部分だけ末尾省略になること。フォント/配置の自動試験は実施済み。
- 左右/上下配置、負座標、画面端、タスクバー位置、狭い作業領域で、候補全体と選択行が画面内へ収まること。実4モニター・全150%で確認済み。
- 異なる倍率（例100%＋150%＋200%）間で入力先を移動し、主ウィンドウがモニターを跨いでもキャレット側の倍率・位置になること。unaware/system aware/per-monitor aware入力先の認識方式別変換は自動試験済み、実混在倍率の移動は未実施。
- 候補表示中の倍率変更・モニター着脱・解像度変更・プライマリ変更でも次の表示で再計測し、旧倍率や旧作業領域に残らないこと。設定変更を伴うこの試験は未実施。
- キャレットを取得できない欄で候補を出さず、マウス位置へ推測表示しないこと。
- 30分以上の連続入力、スリープ復帰、レイアウト変更、GUI表示中のアプリ終了を確認。物理キーボードの連続入力で入力欠落・不正な置換・再帰イベントがないこと。
- 座標取得はWin32のみ。IME ON・半角英数の安全確認時だけフォーカスHWNDへUIA照会すること、ツリー探索・UIA本文取得・イベント購読・IA2参照を行わないことを確認する。ENG/IME OFFではUIAを初期化しないこと。既存側の高コスト探索回数の厳密計測は未実施。

## UIA入力欄の追加試験

- `tests/uia-fixture.html`の通常input・textarea・role=textboxのcontenteditableで、IME OFFの`confi`から候補表示・選択・語尾追加を確認する。初回のキー試験ではLearning=0にし、別の学習試験で既定Learning=1へ戻して未知語2回・既知語の回数更新を確認する。
- password・readonly・disabled・選択範囲・キャレット不明・TextPattern/readonly属性非対応では停止すること。Documentやページ本文全体を入力欄と扱わないこと。

- UIA照会中のIME ON切替、フォーカス変更、入力割込みでは確定を中止すること。変換モードEnterで改行/送信を同時に実行せず、選択前Enterは入力先へ渡すこと。
- UIAキャレット矩形が物理座標で正しく表示され、異なるDPIのモニター移動でも候補が入力欄近傍に収まること。
